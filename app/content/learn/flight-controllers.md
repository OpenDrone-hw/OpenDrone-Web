# Flight Controllers and Their Firmware: Research Notes

Research pass completed 2026-08-12. One claim per bullet, each ending in source
URL(s) and a confidence tag: [verified] = two independent sources or one primary
source, [single] = one secondary source only. Six bullets are marked CORRECTION
and overturn a claim that is widely repeated elsewhere: check those first before
reusing any existing summary of this history.

Method note: many of the strongest claims below come from direct inspection of
the git object graph, via authenticated `gh api` calls and `git clone
--filter=blob:none` of the actual repositories. Commit hashes and author dates
are quoted verbatim from those clones, so they are primary evidence rather than
secondary reporting.

## Firmware lineage (family tree with dates)

Three independent trees, not one. Each is a single unbroken git history from
its own root commit. Dates are first commit or project start where known,
repository creation otherwise, and end dates are the last commit on the
default branch.

```
HOBBY / RACING TREE  (GPLv3, root commit d262c6e, 2012-02-16, timecop)
  KKmulticopter          2009-11-16 .. ~2013     Rolf Bakke, AVR asm, no accel
                                                 (separate codebase, NOT an
                                                  ancestor of the tree below)
  MultiWii               2010-06-16 .. 2016-02   Alexandre Dubus, Wii sensors
    +-- Baseflight       2012-02-16 .. 2016-01   timecop, MultiWii to STM32
          +-- Cleanflight  2013-03-27 .. 2020-09   Dominic Clifton
          |     +-- iNav       2015-03-13 .. live    Konstantin Sharlaimov
          |     +-- Betaflight 2015-06-08 .. live    Boris B
          |           +-- EmuFlight 2019-07-15 .. live
          +-- (Cleanflight back-merged Betaflight in 2020, then stopped)

OPENPILOT TREE  (root commit 2009-11-28, David Ankers)
  OpenPilot              2009-11-28 .. 2015-05   collapsed over domain/forum control
    +-- Tau Labs         2012-11-08 .. 2017-01   first named PhoenixPilot
    |     +-- dRonin     2015-10-04 .. 2021-06
    +-- LibrePilot       2015-06-23 .. 2019-02   12 signatories, board governance

AUTONOMY TREE  (two projects, one shared hardware platform, split by licence)
  DIY Drones community   2007-05
  ArduPilot   GPLv3      2009-05 board, 2010-05-14 oldest commit .. live
  PIXHAWK @ ETH Zurich   2008-10, team assembled 2009-01
    +-- MAVLink          2010-04-02 oldest commit .. live  (LGPLv3 + MIT exception)
    +-- PX4     BSD-3    2012-07-25 announced .. live
  Pixhawk hardware       2013-08-29, jointly PX4 + 3DR + ArduPilot
  Dronecode              2014-10-13 formed; ArduPilot leaves 2016-09-09
```

Cross-links between the trees, all verified below: Cleanflight adopted the
OpenPilot CC3D in 2014-07 and the Tau Labs Sparky in 2014-12; LibrePilot
adopted Cleanflight-era SPRacingF3 targets in 2017-05; MSP, written for
MultiWii in 2012-04, is still in Betaflight in 2026; and the Pixhawk 1 used the
same ST L3GD20 gyro family that Cleanflight had drivers for.

### Root: the Baseflight commit

- The Baseflight lineage begins at commit `d262c6e66c7862441c5a7e52248f4daf7ae12e2f`, authored by `timecop` on 2012-02-16 09:39:58 +0000, with the message "imported STM32 multiwii port into baseflight dir": this independently confirms the previously reported 2012-02-16 date. Source: `git log --reverse` on a fresh clone of https://github.com/multiwii/baseflight [verified]
- That root commit's author email is `timecop@7c89a4a9-59b9-e629-4cfe-3a2d53b20e61`, a Google Code Subversion repository UUID, which shows the git history was imported from SVN by git-svn and that 2012-02-16 is the original SVN commit date rather than a git-era date. Source: `git log --format='%ae'` on https://github.com/multiwii/baseflight [verified]
- Baseflight's own GitHub repository `multiwii/baseflight` was not created until 2012-09-05, roughly seven months after the first commit, so repo creation date and project start date differ and must not be conflated. Source: `gh api repos/multiwii/baseflight` field `created_at` = 2012-09-05T15:27:39Z [verified]
- Baseflight, as the first commit message states, was a port of MultiWii to STM32, not an independent codebase: the repository description is "32 bit fork of the MultiWii RC flight controller firmware". Source: https://github.com/multiwii/baseflight [verified]
- Cleanflight, Betaflight, iNav and EmuFlight all share the identical root commit `d262c6e66c7862441c5a7e52248f4daf7ae12e2f`, which is cryptographic proof that all four are unbroken descendants of timecop's 2012-02-16 Baseflight import. Source: `git rev-list --max-parents=0 HEAD` run on clones of https://github.com/cleanflight/cleanflight, https://github.com/betaflight/betaflight, https://github.com/iNavFlight/inav, https://github.com/emuflight/EmuFlight [verified]
- Baseflight's last commit on master is dated 2016-01-06, and its final release tag is `release_2015-08-27`, so the project was effectively dead by early 2016 after Cleanflight and Betaflight had taken over. Source: `git log -1` and `git for-each-ref refs/tags` on https://github.com/multiwii/baseflight [verified]
- Baseflight only ever used date-stamped release tags, nine in total, running from `release_2014-10-01` (tagged 2014-10-24) to `release_2015-08-27`: it never adopted semantic versioning. Source: `git for-each-ref --sort=creatordate refs/tags` on https://github.com/multiwii/baseflight [verified]
- Baseflight was licensed GPLv3, and its README states the inheritance explicitly: "baseflight is licensed under GPL V3 (just like MultiWii code it originated from)". Source: `git show HEAD:README.md` on https://github.com/multiwii/baseflight [verified]
- The Baseflight README carries a license exception targeted at one named individual: "if the developer viewing or updating the code is named 'dominic clifton', the modified 'hydraIRC limited-use source license' applies", which then forbids exactly what Clifton had done, namely "Use the source to create derivative works. (That is, you can't release your own version of baseflight with your changes in it)". Source: commit d25564e26b3050ba1c895e505ac7f7cf6c4be3cd on https://github.com/multiwii/baseflight [verified]
- That clause was added by `dongie` (timecop) on 2014-06-04 15:09:15 +0900 in commit d25564e, a 29-line addition to README.md titled only "Update README.md": the Baseflight/Cleanflight schism is therefore documented in the parent project's own license text, with a precise date. Source: `git show d25564e` on https://github.com/multiwii/baseflight [verified]
- The clause was added roughly 14 months after Cleanflight's repository was created on 2013-03-27, so it was a reaction to the fork rather than a pre-existing condition. Source: commit date of d25564e versus `gh api repos/cleanflight/cleanflight` `created_at` [verified]
- The barb is pointed: the "hydraIRC limited-use source license" is Dominic Clifton's own license from his HydraIRC project, so timecop applied Clifton's restrictive license back against Clifton personally. Source: the README text citing http://www.hydrairc.com/content/developers, and Clifton's use of the handle `hydra` [verified]
- The clause explicitly limits its own scope, stating "note that above exception is strictly name-based and does not apply to general developers who wish to contribute to baseflight", and a later revision of the README appends the line "4) YHBT.", internet shorthand for "you have been trolled", consistent with timecop's GitHub handle `trollcop`. Source: `git show HEAD:README.md` and `git show d25564e` on https://github.com/multiwii/baseflight [verified]
- No claim is made here about whether the name-based exception is legally effective against a GPLv3 grant: it is recorded as a historical artefact of the split, not as a legal conclusion. Source: the README text itself [verified]
- Baseflight's README documents the era's infrastructure: an IRC channel "#multiwii on Freenode", a Jenkins build server at dev.baseflight.net:8080, and a Chrome Web Store configurator app, all now defunct. Source: `git show HEAD:README.md` on https://github.com/multiwii/baseflight [verified]
- The "Naze" build target is first named in a Baseflight commit on 2012-06-19 by timecop, "Now properly builds both Naze and FY90Q targets", which dates the Naze32 board lineage to no later than mid-2012 and shows it shared the firmware with an earlier FY90Q target. Source: `git log -i --grep='naze' --reverse` on https://github.com/multiwii/baseflight [verified]
- Baseflight accumulated 855 commits over its whole life, against 16589 in Cleanflight and 19755 in Betaflight as of 2026-08, a useful measure of how much the forks outgrew the parent. Source: `git rev-list --count HEAD` on each clone [verified]

### KKmulticopter, the pre-MultiWii era

- Rolf R. Bakke, RCGroups handle `kapteinkuk`, opened the founding thread "Build KapteinKUKs Simple and Low Part Count Quad, Hex and Tricopter Flight Controller" on 2009-11-16, RCGroups thread id 1143569: this is the earliest primary artefact of the KK line and predates MultiWii by seven months. Source: https://web.archive.org/web/20100705135834/http://www.rcgroups.com/forums/showthread.php?t=1143569 [verified]
- Bakke's RCGroups account join date is July 2008, his post count was 388 in July 2010 and 914 by May 2013, and his forum title had become "Quad Whisperer". Source: Wayback snapshots of RCGroups thread 1143569 from 2010-07 and 2013-05 [verified]
- The original KK controller firmware was written in AVR assembly and released with the schematic in the opening post, explicitly so others could build their own. Source: https://web.archive.org/web/20100705135834/http://www.rcgroups.com/forums/showthread.php?t=1143569 [verified]
- The original KK board used an ATmega48/88/168/328 running on the 8 MHz internal RC oscillator with no crystal, BODLEVEL 1.8 V. Source: https://web.archive.org/web/20100705135834/http://www.rcgroups.com/forums/showthread.php?t=1143569 [verified]
- The original KK board had NO accelerometer: its sensors were three single-axis HobbyCity HK401B RC heading-hold gyros at 13 dollars each, harvested for their gyro element and glued to the PCB, giving rate-only "acro" stabilisation. Source: https://web.archive.org/web/20100705135834/http://www.rcgroups.com/forums/showthread.php?t=1143569 [verified]
- The KK design cannibalised the donor gyros for passives too: the V5 SMD bill of materials reuses the HK401B's 3314j trim potentiometers and 47 uF tantalums. Total build cost quoted by Bakke was about 60 dollars. Source: https://web.archive.org/web/20100705135834/http://www.rcgroups.com/forums/showthread.php?t=1143569 [verified]
- KK board revisions in the opening post are V4 through-hole, V5 SMD and V6 through-hole (5 x 5 cm double-sided, with SeeedStudio Gerbers), and firmware was published as a separate binary per airframe: tricopter, quadcopter, hexacopter and Y6. Source: https://web.archive.org/web/20100705135834/http://www.rcgroups.com/forums/showthread.php?t=1143569 [verified]
- kkmulticopter.com was NOT Bakke's own site: it was a community site run by "Niall", whose own about text reads "The KKmulticopter project was started by Rolf Bakke aka KapteinKuk, and the KK in the name of the project is in his honour". Earliest snapshot 2010-06-03. Source: https://web.archive.org/web/20100603140327/http://www.kkmulticopter.com/ [verified]
- kkmulticopter.kr, a separate Korean site and the source of the "Blueboard" and "Redboard" clones, is archived from 2010-10-15. Source: http://web.archive.org/cdx/search/cdx?url=kkmulticopter.kr [verified]
- HobbyKing sold at least four pre-KK2 clone families, all listed as supported targets by the flash tool: Quadcopter Control Board V1 and V2/V2.1, Multi-Rotor Control Board V3, KK Plus V5.5d/e, the Korean Blueboard and Redboard, and the Flycam/DealExtreme Blackboard. Source: https://lazyzero.de/en/modellbau/kkmulticopterflashtool/start [verified]
- CORRECTION to a common claim: KK2.0 used an Atmel ATmega324PA with 32 KB flash, NOT a 644PA. Source: https://web.archive.org/web/20120623030053/http://www.hobbyking.com/hobbyking/store/__24723__Hobbyking_KK2_0_Multi_rotor_LCD_Flight_Control_Board.html [verified]
- KK2.0 appeared in the HobbyKing catalogue by 2012-06-23 at 29.99 dollars, marketed as "Designed by the Grand father of the KK revolution, Rolf R Bakke, exclusively for HobbyKing", and it brought the KK line its first auto-level function via a dual-chip InvenSense 3-axis gyro plus an Analog Devices 3-axis accelerometer. Source: https://web.archive.org/web/20120623030053/http://www.hobbyking.com/... [verified]
- The KK2.0 listing states "Royalties paid on each unit sold to Rolf R Bakke, the original KK Designer", the only concrete commercial arrangement found for any early hobby flight controller designer. Source: https://web.archive.org/web/20120623030053/http://www.hobbyking.com/... [verified]
- KK2.0 rolled out across HobbyKing regional warehouses through late 2012 into 2013: AU SKU 30762 (2012-11), UK SKU 31656 (2012-12), NL/EU SKU 34542 (2013-02), DE SKU 37983 (2013-03), and it was bundled into the Turnigy Micro Quad V2 RTF/PNP from 2012-10. Source: http://web.archive.org/cdx/search/cdx?url=hobbyking.com&matchType=domain&filter=urlkey:.*kk2.* [verified]
- KK2.1.5 is the ATmega644PA board: "KK2.1.5 Multi-rotor LCD Flight Control Board With 6050MPU And Atmel 644PA", earliest Wayback capture 2014-03-17, 29.99 dollars, with the three discrete sensors replaced by a single InvenSense MPU-6050. Source: https://web.archive.org/web/20140317171820/http://www.hobbyking.com/... [verified]
- The KK line therefore made the same discrete-to-integrated sensor transition as MultiWii, but two years later: MultiWii adopted the MPU6050 in 2012-01, KK2.1.5 in 2014-03. Source: MultiWii commit history and the KK2.1.5 product page [verified]
- The founding KK thread grew to 156 pages by 2010-07, 811 pages by 2013-05, 813 by 2013-12 and only 816 by 2025-03: the project was effectively finished by the end of 2013. Source: Wayback snapshots of RCGroups thread 1143569 across those dates [verified]
- The KKmulticopter Flash Tool was written by Christian Moll (GitHub `lazyzero`, Germany), a Java GPLv3 front end to avrdude aimed at users who had never flashed a microcontroller, shipping in 27 languages with firmware fetched from an online repository Moll maintained. Source: https://lazyzero.de/en/modellbau/kkmulticopterflashtool/start [verified]
- The flash tool was already at version 0.19 by 2011-04-13 and its changelog references a bug affecting versions older than 0.11, so the project predates April 2011. Source: https://web.archive.org/web/20110523232215/http://lazyzero.de/en/modellbau/kkmulticopterflashtool [verified]
- The flash tool expanded far beyond KK boards, flashing SimonK and Wii-ESC firmware onto ATmega8-based brushless ESCs: it became a general-purpose entry point into ESC reflashing, which is the direct ancestor of the BLHeli and AM32 tooling culture. Source: https://lazyzero.de/en/modellbau/kkmulticopterflashtool/start [verified]
- The flash tool source reached GitHub as `lazyzero/kkMulticopterFlashTool` on 2014-01-09, last pushed 2021-09-06, with 25 stars and 7 forks. Source: https://api.github.com/repos/lazyzero/kkMulticopterFlashTool [verified]

### MultiWii

- The founding RCGroups thread "MultiWiiCopter (previously TriWiiCopter)", thread id 1261382, was started by Alexinparis on 2010-06-16: the original title shows the project began as a TRIcopter build, not a quad. Source: https://web.archive.org/web/20110610144932/http://www.rcgroups.com/forums/showthread.php?t=1261382 [verified]
- Alexinparis's RCGroups profile gives a join date of June 2009 and a location of Paris, France, consistent with Alexandre Dubus. Source: https://web.archive.org/web/20110610144932/http://www.rcgroups.com/forums/showthread.php?t=1261382 [verified]
- The opening post states the premise verbatim: "The MultiWiiCopter is another multicopter based on a Wii Motion Plus extension and an Arduino pro mini board. I wanted to design something very simple, cheap, minimalist, with an open source code." Source: https://web.archive.org/web/20110610144932/http://www.rcgroups.com/forums/showthread.php?t=1261382 [verified]
- CORRECTION to a common claim: the Nunchuk accelerometer MultiWii used was an ST LIS3L02AL, not an ADXL330. The Wii Motion Plus gyros were two InvenSense IDG-650 plus one ISZ-650. Source: https://web.archive.org/web/20110206013119/http://code.google.com/p/multiwii/ [verified]
- The Nunchuk was optional from the start: "The integration of Wii nunchuk allows an auto stable mode but is not mandatory to fly the model", so MultiWii, like the KK board, could fly rate-only. Source: https://web.archive.org/web/20110206013119/http://code.google.com/p/multiwii/ [verified]
- The economic argument for the Wii hack is stated on multiwii.com itself: InvenSense gyros "are relatively expensive" bought standalone, while Chinese Wii Motion Plus copies cost "10 or 15 dollars". The hack was about price, not novelty. Source: https://web.archive.org/web/20110204055353/http://www.multiwii.com/ [verified]
- multiwii.com documented the reverse engineering directly, covering cost, dimensions, the integrated ADC, the communication protocol and the I2C bypass mode of the Nunchuk, and cited wiibrew.org: the console-hacking wiki was the actual engineering reference. Source: https://web.archive.org/web/20110204055353/http://www.multiwii.com/ [verified]
- The Google Code project code.google.com/p/multiwii is archived from 2011-02-06, owner account `dubu...` (masked by Google Code), with 3 committers, 0 contributors, licence GPLv3, and a feature list of only TRICOPTER, QUAD +, QUAD X and HEX Y6 at that point. Source: https://web.archive.org/web/20110206013119/http://code.google.com/p/multiwii/ [verified]
- MultiWii release timeline from the project's own download index: 1.7 and 1.9 (2011-11), 1.8 patch 2 (2011-09), 2.0 (2012-03), 2.1 (2012-07), 2.2 (2013-03), 2.3 (2013-11). Source: https://web.archive.org/web/20140807084845/https://code.google.com/p/multiwii/downloads/list [verified]
- The `multiwii` GitHub organisation was created 2012-07-19 and the firmware mirror the next day: GitHub was a MIRROR, not a migration target, and Google Code SVN remained authoritative for the project's whole life. Source: https://api.github.com/repos/multiwii/multiwii-firmware [verified]
- Baseflight was created on 2012-09-05 INSIDE the `multiwii` GitHub organisation, so the STM32 port began as an official MultiWii-org project before it forked away: the lineage was institutional, not just textual. Source: https://api.github.com/orgs/multiwii/repos [verified]
- Commit counts by author in the MultiWii mirror: dubusal (Alexandre Dubus) 300 across two identities, der.fliegende.hamburger ("Hamburger") 195, nils.tholen 54 across three identities, Emilsson69 46, romek_b 43, stefan 43, Felix Niessen ("ronco") 39, Danal Estes 38, virtume2 26, eosbandi 14. Source: `git shortlog` on https://github.com/multiwii/multiwii-firmware [verified]
- Hamburger was by a wide margin MultiWii's second most active developer at 195 commits against Dubus's 300, and he authored CREDITS.txt itself as well as the power meter, telemetry over LCD/OLED and flying wing mixing. Source: `git shortlog` and CREDITS.txt on https://github.com/multiwii/multiwii-firmware [verified]
- The move off Wii parts to dedicated I2C breakouts had ALREADY happened by mid-2011: the earliest preserved revision in the mirror (2011-06-19, SVN trunk r168) already contains ITG3200, BMA020, L3G4200D and FreeIMU support. The Wii-sensor era of MultiWii lasted roughly one year. Source: `git log -S` on https://github.com/multiwii/multiwii-firmware and https://web.archive.org/web/20110610144932/http://www.rcgroups.com/forums/showthread.php?t=1261382 [verified]
- MPU6050 support entered MultiWii on 2012-01-06 in a commit by dubusal, so the single-chip 6-axis MEMS era began with MultiWii 2.0 and 2.1, and it entered Baseflight two months later on 2012-03-17. Source: `git log -S "MPU6050"` on https://github.com/multiwii/multiwii-firmware [verified]
- CRIUS board support was added to MultiWii on 2012-02-20 by contributor virtume2, marking the arrival of purpose-built commercial MultiWii boards. Source: `git log -S "CRIUS"` on https://github.com/multiwii/multiwii-firmware [verified]
- HobbyKing's own MultiWii hardware line appears from 2012-09: MultiWii SE V2.0 (2012-09-03), MultiWii PRO with MTK GPS (2012-09-11), MultiWii 328P (2012-09-11), MultiWii Lite V1.0 (2012-09-12). Source: http://web.archive.org/cdx/search/cdx?url=hobbyking.com&matchType=domain&filter=urlkey:.*multiwii.* [verified]
- At least 11 distinct MultiWii SKUs existed at HobbyKing alone, including MicroWii and NanoWii ATmega32U4 boards by 2013-01, a MultiWii Mini with separate HMC5883L compass and BMP085 barometer modules from 2012-12, and a "Multiwii and Megapirate AIO Flight Controller" by 2013-06. Source: http://web.archive.org/cdx/search/cdx?url=hobbyking.com&matchType=domain&filter=urlkey:.*multiwii.* [verified]
- Google Code download counts as of 2014-08: version 2.1 79,073, 2.2 77,781, 2.3 77,495, 2.0 42,522, 1.9 41,034, 1.8 patch 2 15,485, 1.7 12,459, plus dev r1648 at 24,766, totalling over 370,000 downloads. Source: https://web.archive.org/web/20140807084845/https://code.google.com/p/multiwii/downloads/list [verified]
- The RCGroups MultiWii thread reached 1,031 pages by 2011-06 and 1,998 pages by 2017-04, roughly 30,000 posts at 15 posts per page. Source: Wayback snapshots of RCGroups thread 1261382 from 2011-06 and 2017-04 [verified]
- Hackaday covered MultiWii retrospectively on 2015-04-19, and a top comment the next day already observed "Most people have moved on to STM32 based flight controllers running (multiwii derivatives) baseflight or cleanflight": the handover was publicly acknowledged by early 2015. Source: https://hackaday.com/2015/04/19/multicopters-and-their-multiwii-beginnings/ [verified]

### MSP, the protocol that outlived everything

- The MultiWii Serial Protocol was introduced on 2012-04-09, in a dubusal commit titled "merging _shared + New Serial Protocol: huge modification", which added the `MSP_*` message identifiers. Source: `git log -S "MSP_IDENT"` on https://github.com/multiwii/multiwii-firmware [verified]
- MSP is absent from MultiWii 2.0 (2012-03) and present in MultiWii 2.1 (2012-07), so 2.1 is the first release to ship it, and the header in `Serial.ino` reads "// Multiwii Serial Protocol 0" with `#define MSP_VERSION 0`. Source: https://github.com/multiwii/multiwii-firmware/blob/release-2.1/Serial.ino [verified]
- The original 2012 MSP command numbering survives unchanged in Betaflight today: MSP_STATUS 101, MSP_RAW_IMU 102, MSP_ATTITUDE 108, MSP_SET_RAW_RC 200. Source: https://github.com/betaflight/betaflight/blob/master/src/main/msp/msp_protocol.h [verified]
- Betaflight's protocol header still carries the comment "Additional non-MultiWii commands (150-166)" and refers to "the legacy MSP_IDENT command", and Cleanflight retains `#define MULTIWII_IDENTIFIER "MWII"`: the 2010 Wii hack is still named in the source of 2026 firmware. Source: https://github.com/betaflight/betaflight/blob/master/src/main/msp/msp_protocol.h and https://github.com/cleanflight/cleanflight/blob/master/src/main/msp/msp_protocol.h [verified]
- MSP has therefore been in continuous production use for 14 years, from MultiWii 2.1 in 2012-07 to Betaflight 2026.6.1 on 2026-08-02: it is the single most durable artefact of the entire hobby lineage. Source: the commit and release dates above [verified]

- The MultiWii firmware GitHub mirror `multiwii/multiwii-firmware` was created on 2012-07-20 and is explicitly described as a "GitHub mirror of the official SVN multiwii project", so its earliest commit is a mirror artefact and not the true project start. Source: `gh api repos/multiwii/multiwii-firmware` [verified]
- The earliest commit in the MultiWii GitHub mirror is dated 2011-10-26 by the author `buga`, message "initial BTSERIAL code": this is a lower bound on the project's age, not its origin, since MultiWii predates the mirror. Source: `git log --reverse` on https://github.com/multiwii/multiwii-firmware [verified]
- The MultiWii mirror stopped receiving commits on 2022-05-27 and holds 773 commits total. Source: `gh api repos/multiwii/multiwii-firmware` field `pushed_at`, and `git rev-list --count HEAD` [verified]
- The MultiWii source code itself is primary evidence of the Wii Motion Plus origin: `Sensors.cpp` defines `WMP_ADDRESS_1 0x53` and `WMP_ADDRESS_2 0x52`, writes `0x55` to register `0xF0` to "Initialize Extension" and `0x05` to register `0xFE` to "Activate Nunchuck pass-through mode". Source: `git show HEAD:Sensors.cpp` on https://github.com/multiwii/multiwii-firmware [verified]
- The MultiWii gyro read code contains the comment "we detect here the slow of fast mode WMP gyros values (see wiibrew for more details)", an explicit citation of the WiiBrew console-hacking wiki inside flight controller firmware. Source: `git show HEAD:Sensors.cpp` on https://github.com/multiwii/multiwii-firmware [verified]
- MultiWii's `config.h` documents the I2C constraint the Wii hardware imposed: "#define I2C_SPEED 100000L //100kHz normal mode, this value must be used for a genuine WMP" versus "400kHz fast mode, it works only with some WMP clones", which shows genuine Nintendo parts capped the sensor bus at 100 kHz. Source: `git show HEAD:config.h` on https://github.com/multiwii/multiwii-firmware [verified]
- WMP remained a selectable sensor option in MultiWii to the very end of the project: `#define WMP` is still present in `config.h` at HEAD alongside dozens of dedicated sensor boards. Source: `git show HEAD:config.h` on https://github.com/multiwii/multiwii-firmware [verified]
- MultiWii's `config.h` at HEAD lists over thirty supported sensor boards spanning the whole transition away from Wii parts, including ITG3200 plus BMA180 combinations (DROTEK_10DOF, INNOVWORKS_10DOF, Bobs_9DOF_V1), ITG3205 plus ADXL345 (GY_85, OPENLRSv2MULTI), L3G4200D plus ADXL345 (GY_80) and MPU6050 boards (GY_521, GY_86, GY_88, CRIUS_SE_v2_0, DROTEK_6DOF_MPU, FREEIMUv04, NANOWII, MICROWII). Source: `git show HEAD:config.h` on https://github.com/multiwii/multiwii-firmware [verified]

- Felix Niessen, who founded the KISS flight controller and ESC ecosystem, is credited in MultiWii under the forum handle "ronco": KISS's founder came directly out of the MultiWii contributor community. Source: `git show HEAD:CREDITS.txt` on https://github.com/multiwii/multiwii-firmware [verified]

#### Cleanflight: release history and end of life

- Dominic Clifton's first commit in the Cleanflight history is dated 2013-04-06, message "OLIMEXINO - Initial support for the OLIMEXINO board", which shows the project's opening move was multi-board support rather than flight behaviour changes. Source: `git log --author='Dominic' --reverse` on https://github.com/cleanflight/cleanflight [verified]
- Cleanflight's first tags are `flight-ready-1` and `flight-tested-1`, both dated 2013-08-28, marking about five months from repo creation to a flyable build. Source: `git for-each-ref --sort=creatordate refs/tags` on https://github.com/cleanflight/cleanflight [verified]
- Cleanflight v1.0.0 was tagged 2014-11-24, and the project then released at a very high cadence: v1.1.0 2014-12-16, v1.2.0 2014-12-21, v1.3.0 2014-12-28, v1.4.0 2015-01-03, v1.5.0 2015-01-09, v1.6.0 2015-01-16, six minor releases in under two months. Source: `git for-each-ref --sort=creatordate refs/tags` on https://github.com/cleanflight/cleanflight [verified]
- Cleanflight 2.0.0 was tagged `CLFL_v2.0.0` on 2017-04-13, and the tag prefix changed to `CLFL_` at that point, apparently to disambiguate from Betaflight tags in the shared history. Source: `git for-each-ref refs/tags` on https://github.com/cleanflight/cleanflight [verified]
- Cleanflight's last conventional release was `CLFL_v2.5.0` on 2019-01-10, after which the version numbering jumped to `CLFL_v4.2.0-RC1` on 2020-05-21 through `CLFL_v4.2.0-RC3` on 2020-06-04: the jump from 2.5 to 4.2 matches Betaflight's version numbers, indicating Cleanflight re-based itself onto Betaflight rather than continuing independently. Source: `git for-each-ref --sort=creatordate refs/tags` on https://github.com/cleanflight/cleanflight [verified]
- Cleanflight's final commit on master is dated 2020-09-08 and is titled "Merge pull request #3112 from cleanflight/bf-merge-20200907": the last act of the parent project was to merge its own descendant's code back in. Source: `git log -1 master` on https://github.com/cleanflight/cleanflight [verified]
- Because of that 2020 back-merge, the git merge-base between Cleanflight and Betaflight is commit `8f2d21460` dated 2020-06-14 by Michael Keller, NOT the 2015 fork point: anyone computing the fork date from merge-base will get the wrong answer. Source: `git merge-base master p/master` between clones of the two repositories [verified]
- Cleanflight never reached a `CLFL_v4.2.0` final tag, only three release candidates, so version 4.2 was abandoned mid-cycle. Source: `git for-each-ref refs/tags` on https://github.com/cleanflight/cleanflight [verified]
- THE ACRIMONIOUS-SPLIT NARRATIVE DOES NOT SURVIVE THE RECORD. Betaflight's own FAQ describes the fork as intentional and two-way: Boris "decided that he could possibly make improvements on the way the PID control loop works and forked an Experimental version as BetaFlight", and "This code merge (in both directions) has already started happening from BetaFlight V2.4.0 and CleanFlight V1.12 onwards". Source: https://betaflight.com/docs/wiki/guides/current/FAQ [verified]
- Boris B's own stated reason for eventual divergence was workload, not conflict: "maintaining multiple versions is really time consuming and not efficient....well actually impossible", with a three-way scope split of Cleanflight wide, iNav autonomous, Betaflight acro and level. Source: https://betaflight.com/docs/wiki/guides/current/FAQ [verified]

Source: https://github.com/betaflight/betaflight-configurator/issues/2023 and /2024 [verified]

Source: https://github.com/cleanflight/cleanflight/pull/3092 [verified]

### Raceflight, FlightOne, and the GPL litigation

This video only applies to the 'BB' versions of RF". Source: https://www.youtube.com/watch?v=T-OHTvzL07U [verified]

Source: https://blog.quadmeup.com/2017/12/06/raceflight-one-source-code-has-been-published-and-what-does-that-mean/ [verified]
- A DMCA takedown was filed the SAME DAY, 2017-12-05, by Code Orange Inc. against `rs2k/RaceFlight-One`, claiming "The code in question is owned by Code Orange Inc, and employee has posted the code to github ... he improperly licensed it as GPL". Source: https://github.com/github/dmca/blob/master/2017/2017-12-05-CodeOrange.md [verified]

Source: https://github.com/github/dmca/blob/master/2017/2017-12-15-CodeOrange-Counternotice.md [verified]

Source: https://github.com/github/dmca/blob/master/2018/2018-04-03-Raceflight.md [verified]

#### The OpenPilot collapse

- The trigger was disclosed on 2015-06-15: a plan was announced in the closed development chat that David Ankers would leave OpenPilot and fork it into a new project called OPNG. Source: https://raw.githubusercontent.com/librepilot/librepilot.github.io/master/docs/statement_departure.pdf [verified]

- A large part of the development team plus several key members and a significant number of ordinary users were banned from the openpilot.org forums for asking for transparency about OPNG's intentions. Source: https://raw.githubusercontent.com/librepilot/librepilot.github.io/master/docs/statement_departure.pdf [verified]
- The LibrePilot founding statement is dated 2015-07-08 and was signed by twelve people: Fredrik Arvidsson, Werner Backes, Paolo Buongarzone, Cliff Geerdes, Anders Johansson, Stefan Karlsson, Karl Knutsson, Laurent Lalanne, Fredrik Larsson, Alessio Morale, Philippe Renon and Mathieu Rondonneau. Source: https://raw.githubusercontent.com/librepilot/librepilot.github.io/master/docs/statement_departure.pdf [verified]
- LibrePilot stated its governance differentiator explicitly: a democratic approach with a board of directors in charge of important decisions, and a willingness to collaborate with similar projects, "something that OpenPilot has not done". Source: https://raw.githubusercontent.com/librepilot/librepilot.github.io/master/docs/statement_departure.pdf [verified]
- The code rename preceded the public statement: commit "Rename to LibrePilot" by James Duley, 2015-06-23, tagged 0.0, two weeks before the 2015-07-08 announcement. Source: https://github.com/librepilot/LibrePilot [verified]
- LibrePilot's releases are 15.09-RC1 (2015-09-28), 15.09 (2015-10-21), 16.09-RC1 (2016-09-04), 16.09-RC2 (2016-10-06) and 16.09 (tag commit 2016-12-12): only two shipped versions in the project's whole life. Source: https://github.com/librepilot/LibrePilot/tags [verified]
- LibrePilot's last commit on the GitHub mirror is 2019-02-21, so the project has been dormant for seven years. Source: https://github.com/librepilot/LibrePilot [verified]
- LibrePilot added Cleanflight-era board targets late in life, including spracingf3 and spracingf3evo (2017-05-22, by Vladimir Zidar), pikoblx (2017-04-26) and tinyfish (2017-05-29): the OpenPilot branch was chasing the Cleanflight branch's hardware by then, not the reverse. #### ArduPilot software and APM hardware

- The first ArduPilot board, using thermopile sensors, was released in May 2009 by Jordi Munoz and 3D Robotics. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- The original ArduPilot code repository was created on Google Code in November 2009 by Jordi Munoz, at code.google.com/p/ardupilot. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- ArduPilot was rewritten from scratch as v2.5 between November 2009 and February 2010 by Jason Short, adding interrupt driven RC input, throttle failsafe, RTL, Loiter, Circle, crosstrack correction, Fly-By-Wire and two-way telemetry. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- The multirotor branch began in May 2010, when ArduPilot merged with AeroQuad, bringing in Jani Hirvinen, and work started on CopterNG. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- In October 2010 the merged AeroQuad/ArduCopter CopterNG project was abandoned and handed to the ArduPirates team, and Jason Short restarted Copter with control logic derived from Plane. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- Mission Planner was released in August 2010 by Michael Oborne. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- Randy Mackay added traditional helicopter support in August 2010, and Doug Weibel flew the first IMU based autonomous plane mission in December 2009 with a modified ArduPilot v2.4. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- The first fully autonomous Copter mission was flown by Jason Short at SparkFun AVC in April 2011. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- In February 2012 Jason Short handed Copter lead development to Randy Mackay, Doug Weibel left to do a PhD, and Andrew "Tridge" Tridgell took over Plane. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- APM1 was released by 3D Robotics in 2010, APM2 in 2011, and APM2.5 and APM2.6 in 2012. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- APM1 used an ATmega1280 as its main MCU, with a separate ATmega328p PPM encoder; APM2.x moved to the ATmega2560 with an ATmega32U2 handling USB and PPM conversion. Source: https://raw.githubusercontent.com/ArduPilot/ardupilot_wiki/master/dev/source/docs/jtag.rst, https://raw.githubusercontent.com/ArduPilot/ardupilot_wiki/master/common/source/docs/common-ppm-encoder-apm2x-atmega32u2.rst and https://raw.githubusercontent.com/ArduPilot/ardupilot_wiki/master/dev/source/docs/building_with_make.rst [verified]
- APM 2.6 is a revision of APM 2.5 that removes the onboard compass, intended for use with the 3DR uBlox LEA-6 GPS with external compass. Source: https://ardupilot.org/copter/docs/common-apm25-and-26-overview.html [verified]
- The AVR based APM boards were retired by code size, not by obsolescence: Copter 3.3 no longer fits on APM, so the last installable Copter build is 3.2.1 and the last Plane build is 3.3.0. This is the clearest documented case of 8-bit AVR flash exhaustion ending an era. Source: https://ardupilot.org/copter/docs/common-apm25-and-26-overview.html [verified]
- Pat Hickey's AP_HAL hardware abstraction layer landed in August 2012 and is what allowed ArduPilot to move off AVR onto other boards. Source: https://ardupilot.org/copter/docs/common-history-of-ardupilot.html [verified]
- ArduCopter release tag dates: 2.1.0-Alpha 2011-11-26, 2.3 2012-02-01, 2.5 2012-03-17, 2.8 2012-10-20, 2.9 2013-01-17, 3.0-rc1 2013-05-01, 3.1.0 2013-12-14, 3.2 2014-11-07, 3.3.1 2015-10-26, 3.4.0 2016-10-31, 3.5.0 2017-07-17, 3.6.0 2018-10-27. Source: https://github.com/ArduPilot/ardupilot/tags [verified]
- ArduCopter 4.x release tag dates: 4.0.0 2019-12-29, 4.1.0 2021-10-07, 4.2.0 2022-05-23, 4.3.0 2022-10-31, 4.4.0 2023-08-18, 4.5.0 2024-04-02, 4.6.0 2025-05-21, 4.7.0 2026-07-20. Source: https://github.com/ArduPilot/ardupilot/tags [verified]
- ArduCopter was already at version 2.3, released 2012-02-01, when timecop made the first Baseflight commit on 2012-02-16: the autonomy branch was roughly two years ahead of the hobby branch in software maturity at the moment the hobby branch started. ## Hardware eras

Method note: the dates below come from `git log --reverse --diff-filter=A` run
against the Betaflight repository, which contains the unbroken 2012 to 2026
history of the whole Baseflight lineage. That gives the exact date a given chip
driver or MCU port first entered the source tree, which is primary evidence.
`git tag --contains` then gives the first shipping release. A caveat worth
recording: filename greps produce false positives, for example a 2016-10-26
commit "Added PICOBFC target files" matches a search for "PICO" but refers to a
board named PICOBFC and has nothing to do with the RP2350.

### MCU specifications, and why each era ended

- ATmega328P: 8-bit AVR at roughly 1 MIPS per MHz, max 20 MHz and only at 4.5 to 5.5 V, 32 KB flash, 2 KB SRAM, 1 KB EEPROM, no FPU (only a 2-cycle integer multiplier), and exactly ONE USART. Source: https://ww1.microchip.com/downloads/en/DeviceDoc/ATmega48A-PA-88A-PA-168A-PA-328-P-DS-DS40002061B.pdf and https://www.microchip.com/en-us/product/atmega328p [verified]
- The single USART is the underrated killer: on a flight controller that is receiver OR telemetry OR GPS, never all three, which is why MultiWii-era boards leaned on softserial and I2C for everything else. Source: the ATmega328P datasheet above [verified]
- The F1 successor was 3.6 times the clock, 4 times the flash and 10 times the SRAM of the ATmega328P, plus 3 USARTs: STM32F103 is a Cortex-M3 at up to 72 MHz with no FPU, 20 KB SRAM on medium-density parts, and 64 KB (F103C8) or 128 KB (F103CB) flash. Source: https://www.st.com/en/microcontrollers-microprocessors/stm32f103.html and the CMSIS device header [verified]
- STM32F303 added the single-precision FPU at the same 72 MHz, with 40 KB SRAM including 8 KB CCM, but the die used in flight controllers is capped: ST specifies F303xB/xC as "128 to 256 Kbytes of Flash memory", so 256 KB is a hard ceiling. Source: https://www.st.com/en/microcontrollers-microprocessors/stm32f303cc.html [verified]
- That 256 KB ceiling killed the F3 over three releases, and the process is documented in the release notes. Betaflight 3.5.0 (2018-08): the firmware would "overflow the available space on a number of F3 based flight controllers", with features cut from ten named targets. Source: https://github.com/betaflight/betaflight/releases/tag/3.5.0 [single]
- Betaflight 4.0.0 (2019-04): overflow now hit "almost all F3 based flight controllers", 18 targets were named, and "the following features had to be removed from all F3 based flight controllers in order to make the firmware fit into flash: Smart Feedforward, support for flashing / configuration of SimonK based ESCs". Source: https://github.com/betaflight/betaflight/releases/tag/4.0.0 [single]
- The same release removed LED strip status display from F3 "in order to be able to reclaim some flash space", and when even that was insufficient introduced "a system of classifying F3 based flight controllers into a number of 'feature cut' levels". Source: https://github.com/betaflight/betaflight/releases/tag/4.0.0 [single]

Source: https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmi270-ds000.pdf [verified]

Betaflight treats its 6400 Hz BMI270 mode as experimental for exactly this reason. Source: https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmi270-ds000.pdf and https://github.com/betaflight/betaflight/blob/master/src/main/drivers/accgyro/accgyro_spi_bmi270.c [verified]
- The user-visible contrast in the popular telling therefore survives, but the mechanism is a register-map restriction, not a physical sensor ceiling: state it that way. Source: the two sources above [verified]
- The BMI270 driver also sets the accelerometer to just 800 Hz (`BMI270_VAL_ACC_CONF_ODR800`), a quarter of the gyro rate. Source: `git show HEAD:src/main/drivers/accgyro/accgyro_spi_bmi270.c` [verified]

Source: `git show HEAD:src/main/drivers/accgyro/accgyro_spi_icm426xx.c` on https://github.com/betaflight/betaflight [verified]

- CORRECTION to the usual explanation: the BMI270's real problem was NOT its sample rate, it was its hardware low-pass cutoff. The Betaflight driver PR states it plainly: "This operation enables the hardware DLPF as normal which has a 751hz 3dB cutoff. As this cutoff is significantly higher than the common Invensense parts, it's expected that the user will be required to enable more software gyro filtering than Betaflight defaults to compensate." Source: https://github.com/betaflight/betaflight/pull/9549 [verified]
- The consequences were physical, not merely a matter of feel: BMI-equipped boards were "much more prone to hot motors, flyaways, and burned ESCs than equivalent MPU/ICM gyro boards" on stock Betaflight defaults. Source: https://github.com/betaflight/betaflight/pull/11400 [single]
- The fix was found by ChrisRosser in pull request #11400, opened 2022-02-12 and merged 2022-03-18, shipping in Betaflight 4.3.0: switching `gyr_bwp` to 0x00 selects OSR4 oversampling, an undocumented behaviour, which "is not explained in the BMI270 datasheet at all but the behaviour is documented in the register map and explained in other Bosch gyro datasheets". Source: https://github.com/betaflight/betaflight/pull/11400 [verified]

- The author verified the real cutoff experimentally rather than trusting the datasheet, by tapping the gyro with a coin and analysing the impulse response: "The DLPF in the BMI270 is a 3rd order filter (18dB/Octave) and in OSR4 mode the 3dB cutoff is ~300Hz." Source: https://github.com/betaflight/betaflight/pull/11400 [single]

### Gyro datasheet specifications, for the parts that mattered

- Gyro noise density ranking across the parts used in FPV, best to worst: ICM-42688-P and LSM6DSV16X 2.8 mdps per root Hz, LSM6DSO and ICM-42605 3.8, ICM-20602 4.0, MPU-6000 and MPU-6050 5.0, BMI160 and BMI270 (performance mode) 7.0, BMI270 (normal mode) and MPU-6500 10.0. Source: the individual datasheets cited in the following bullets [verified]
- The MPU-6500 is TWICE as noisy as the MPU-6000 it succeeded, 10 versus 5 mdps per root Hz: newer did not mean quieter, which is the sourced basis for the era's complaints about MPU-6500 boards. Source: https://www.lcsc.com/datasheet/C50278.pdf and https://www.lcsc.com/datasheet/C24112.pdf [verified]
- MPU-6050 and MPU-6000 are the same die with different bonding, stated verbatim in the shared datasheet: "The MPU-6000 and MPU-6050 are identical, except that the MPU-6050 supports the I2C serial interface only, and has a separate VLOGIC reference pin." Source: https://www.lcsc.com/datasheet/C24112.pdf [verified]
- The I2C-only limitation of the MPU-6050 is physical, not a configuration bit: pin 8 is /CS on the 6000 but VLOGIC on the 6050, and pin 9 is AD0/SDO on the 6000 but AD0 only on the 6050. A 6050 has no chip-select or data-out pin to run SPI on. Source: https://www.lcsc.com/datasheet/C24112.pdf [verified]
- The MPU generation carried a split SPI speed limit that later parts removed: 1 MHz for all registers but 20 MHz for sensor and interrupt register reads only. ICM-20602 flattened this to 10 MHz for everything, and the ICM-426xx family to 24 MHz. Source: https://www.lcsc.com/datasheet/C24112.pdf, https://www.lcsc.com/datasheet/C50278.pdf, https://www.lcsc.com/datasheet/C97633.pdf and https://www.lcsc.com/datasheet/C1850418.pdf [verified]
- The MPU-6000's gyro rate collapses from 8 kHz to 1 kHz the moment any hardware DLPF setting is enabled: "Gyroscope Sample Rate, Slow | DLPFCFG=1..6 | 1 kHz". Filtering and rate were mutually exclusive on the part that defined the Naze32 era. Source: https://www.lcsc.com/datasheet/C24112.pdf [verified]
- The ICM-20602 is where the 32 kHz figure actually comes from: its OUTPUT data rate maxes at 8 kHz, but its internal sample rate is 32 kHz with the DLPF bypassed. Source: https://www.lcsc.com/datasheet/C97633.pdf [single]
- The ICM-42688-P's 32 kHz is a genuine output data rate, not an internal one, and TDK's own family table distinguishes it as "32kHz; RTC" against the ICM-42605 and ICM-40607 at "8kHz; No RTC". Source: https://www.lcsc.com/datasheet/C1850418.pdf [single]
- Betaflight nonetheless runs the ICM-42688-P at 8 kHz, not 32 kHz: "(ODR is set to 8kHz in BF)". The headline number is not the number in use. Source: https://github.com/betaflight/betaflight/pull/13351 [single]
- SPI clock ceilings Betaflight actually applies, from the driver constants: ICM-426xx, ICM-456xx and ICM-40609 24 MHz; MPU6000 and MPU6500 20 MHz; BMI270, BMI160 and LSM6DSO 10 MHz; and ICM-20689 just 8 MHz, the lowest of any InvenSense part in the tree. Source: `src/main/drivers/accgyro/` on https://github.com/betaflight/betaflight [single]
- Betaflight 4.4 added a compile-time SPI clock override because 24 MHz proved marginal on some boards: "There was a report of glitches on the raw gyro output of an icm42688 which were resolved by reducing the SPI clock speed." Source: https://github.com/betaflight/betaflight/pull/13346 [single]
- The BMI270's RMS noise climbs steeply with rate: in performance mode at plus or minus 2000 dps it is 123 mdps at 800 Hz, 174 at 1.6 kHz, 302 at 3.2 kHz and 350 at 6.4 kHz. Running a gyro faster costs noise. Source: https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmi270-ds000.pdf [single]
- The BMI270 needs an 8 KB microcode blob uploaded at boot, which is why it was initially unusable on small parts: "this sensor requires a very large configuration file (essentially a 8KB microcode) be uploaded at initialization ... making it only suitable for MCU targets with more than 512KB of flash". Source: https://github.com/betaflight/betaflight/pull/9549 [single]

### Why SPI replaced I2C for gyros

- Betaflight's manufacturer guidelines state the rule outright: "Note that gyroscopes must communicate via SPI; I2C gyros are not supported." Source: https://betaflight.com/docs/development/manufacturer/manufacturer-design-guidelines [single]
- The engineering reason is given in pull request #9444: "I2C connected gyros will not be supported as they are unable to sample at the native rate. This should only affect F3 and older which are no longer supported anyway." Source: https://github.com/betaflight/betaflight/pull/9444 [single]
- The arithmetic, computed from the datasheet bus limits: I2C costs 9 bit-times per byte (8 data plus ACK) plus addressing overhead, so a 14-byte accelerometer-plus-gyro burst is about 156 bit-times, which at 400 kHz is 390 microseconds. That is a hard ceiling of roughly 2.56 kHz with zero CPU left over. Source: derived from https://www.lcsc.com/datasheet/C24112.pdf [verified as arithmetic, the inputs are datasheet figures]
- A gyro-only 6-byte I2C read is about 84 bit-times, 210 microseconds at 400 kHz, giving a ceiling near 4.76 kHz: this is the origin of the widely repeated "I2C is limited to 4 kHz" figure. Source: derived from https://www.lcsc.com/datasheet/C24112.pdf [verified as arithmetic]
- At 100 kHz standard-mode I2C the same 14-byte burst costs 1560 microseconds, a ceiling of about 641 Hz, which is why 400 kHz fast mode was mandatory on MultiWii and Naze-class boards just to clear 1 kHz. Source: derived from the same datasheet limits [verified as arithmetic]
- To sustain 32 kHz a read must complete in 31.25 microseconds; the I2C 14-byte burst at 390 microseconds is over 12 times the budget, so I2C cannot reach 32 kHz in any configuration. Source: derived as above [verified as arithmetic]
- The same 14-byte payload plus one address byte over SPI is 120 bits with no ACKs: 15.0 microseconds at 8 MHz, 6.0 at 20 MHz, 5.0 at 24 MHz. SPI at 20 MHz is roughly 65 times faster than I2C at 400 kHz for identical data, about 50 times from clock rate and 1.3 times from framing overhead. Source: derived from the driver clock constants and datasheet limits [verified as arithmetic]
- The transition is visible in a single product revision: Naze32 rev6 (2015-09) kept the STM32F103CBT6 but "IMU has been changed from MPU6050 to MPU6500", moving the same board from I2C to SPI. Source: https://oscarliang.com/new-naze32-rev6-upgrade-of-rev5/ [single]
- By 2017 the split was settled on new designs, with SPI for the gyro and I2C surviving only for slow sensors: the Matek F405-STD lists "ICM20602 via SPI" alongside "BMP280 (I2C)". Source: https://www.mateksys.com/?portfolio=f405-std [verified]

### The 32 kHz episode, and the retreat from it

- 32 kHz gyro sampling shipped in Betaflight 3.1.0 on 2017-01-25, enabled by `set gyro_use_32khz = ON`: "Usually F4 board will run fine on 32kHz gyro and 16kHz pid loop. 32/32 is slightly too much for CPU. F7 target is now the only one able to run 32kHz/32kHz flawlessly". Source: https://github.com/betaflight/betaflight/releases/tag/v3.1.0 [verified]
- The same release notes name the hardware requirement and exclude the MPU-6000: "only flight controllers with MPU6500, MPU9250, and ICM-series (eg ICM20689) gyro support 32kHz mode". Source: https://github.com/betaflight/betaflight/releases/tag/v3.1.0 [single]
- The commercial driver was RaceFlight, whose board was named after the number: the "RaceFlight Revolt F4 32KHz Flight Controller", sold under that name at multiple retailers, with RaceFlight's own site claiming "The Revolt supports true 32kHz refresh rates across the board". Source: https://hobbyking.com/raceflight-revolt-f4-32khz-flight-controller.html and https://web.archive.org/web/20180224104738/https://raceflight.com/ [verified]
- Scepticism was contemporaneous, not retrospective: an April 2017 review recorded that "some are claiming there are no benefits". Source: https://matthew-evans.info/posts/raceflight-one-and-revolt-thoughts/ [single]
- KISS FC ran at 1 kHz throughout and was the standing counter-example, tabulated as "1kHz only" against Betaflight's 8 kHz and RaceFlight's "Up to 32kHz", with the reviewer finding KISS at 1 kHz felt "just as 'locked in'". Source: https://oscarliang.com/best-looptime-flight-controller/ [single]
- 32 kHz kept breaking under its own CPU budget: issue #7003 (2018-10) reports a Matek F722 at 32/32 with DShot1200 and a 240 MHz overclock where "CPU load is over 100%; gyro/PID loop runs as slow as 23kHz ... This effectively renders this configuration unusable." Source: https://github.com/betaflight/betaflight/issues/7003 [single]
- The rationale document that ended it is issue #7327, "Determine optimal gyro/pid rates", opened 2019-01-02 by joelucid. Source: https://github.com/betaflight/betaflight/issues/7327 [verified]
- Its Nyquist argument: "Both our dynamic and rpm notches don't seem to cover frequencies beyond 1khz, so a filter sampling rate of 2khz would be sufficient in terms of nyquist". Source: https://github.com/betaflight/betaflight/issues/7327 [single]
- Its latency argument, quantified: "Going from 32khz to 2khz loop times thus increases the end-to-end latency from sticks to quad by 1.3%. Clearly this is relatively a very small impact." Source: https://github.com/betaflight/betaflight/issues/7327 [single]
- The decisive framing, that algorithms beat loop rate: "the rpm filter reduces gyro latency by about 1.5ms and D latency by maybe 3ms. This shows how much more important our algorithms are to flight performance than loop time." Source: https://github.com/betaflight/betaflight/issues/7327 [single]
- The real cost was maintainer time, per Betaflight developer fujin: "we spend a good amount of time aggressively optimizing changes in the context of 32kHz gyro sampling mode timing constraints ... instead of the current break 32khz to fix 32khz to break 32khz to fix .. loop we're in." Source: https://github.com/betaflight/betaflight/issues/7327 [single]
- Field reports in that thread said 32 kHz was actually noisier: "Going from 32k down to 8K on the same copter I have found made a big Improvement in performance. (WAYYYYY less filtering needed)". Source: https://github.com/betaflight/betaflight/issues/7327 [single]
- CORRECTION to a widely repeated date: 32 kHz support was removed by pull request #7567, opened 2019-02-12 and merged 2019-02-14, which shipped in Betaflight 4.0.0 on 2019-04-11, NOT in 4.1 in October 2019 as oscarliang.com states. Source: https://github.com/betaflight/betaflight/pull/7567 and https://github.com/betaflight/betaflight/releases/tag/4.0.0, contradicting https://oscarliang.com/flight-controller/ [verified]
- 1 kHz gyro sampling was removed in the same architectural sweep: "1KHz gyro sampling has been removed. This was mainly a legacy item that's always been poorly supported". Source: https://github.com/betaflight/betaflight/pull/9444 [single]
- The modern consensus is that the whole argument was about an imperceptible difference: "the difference between 8K/8K and 8K/4K is imperceptible to 99% of pilots". Source: https://blog.uavmodel.com/understanding-fpv-gyro-and-pid-loop-frequencies-8k-vs-4k-vs-2k/ [single]

### Loop rates: why the gyro sets the pace

- The "looptime" concept predates all the forks: timecop added `looptime` as a CLI setting to Baseflight on 2012-07-20 with a default of 3000 microseconds, and on 2012-07-21 added "allow 0 for looptime to go back to not-rate-limited loop". The looptime wars therefore started in Baseflight in 2012, not in Betaflight. Source: `git log -i --grep='looptime' --reverse` on https://github.com/betaflight/betaflight [verified]
- A 3000 microsecond default looptime is 333 Hz, so the 2012 baseline was roughly one twentieth of the 8 kHz rates that later became normal. Source: the 2012-07-20 commit above [verified]
- CORRECTION to a common attribution: the "Luxfloat" PID controller is a CLEANFLIGHT feature, not a Betaflight one, and it predates Betaflight by four months. Dominic Clifton renamed it on 2015-01-29 with the explanatory message "Rename pidBaseflight to pidLuxFloat since it was never in official baseflight firmware". Source: `git log -i --grep='luxfloat' --reverse` on https://github.com/betaflight/betaflight [verified]
- Nicholas Sherlock added Blackbox logging of pidLuxFloat intermediates the next day, 2015-01-30: the tooling to actually see what a PID controller was doing arrived alongside the controller itself. Source: `git log -i --grep='luxfloat'` on https://github.com/betaflight/betaflight [verified]
- Dynamic notch filtering originates on 2017-05-13 in a commit by `rav`, merged by Martin Budden as pull request #3074 on 2017-05-16: it is a 2017 development, not part of the original Betaflight proposition. Source: `git log -i --grep='dynamic notch' --reverse` on https://github.com/betaflight/betaflight [verified]
- Dual-stage gyro filtering with selectable PT1, Biquad, Butterworth, FIR denoise and fixed-K Kalman options was added by AJ Christensen on 2018-03-21 (pull request #5391), and the dynamic notch was refactored by `KarateBrot` on 2021-08-27. Source: `git log` on https://github.com/betaflight/betaflight [verified]
- The chronology matters for the "why Betaflight won" question: gyro-synced looping (2015-08) came first and was the founder's own work, while the filtering sophistication that people now associate with Betaflight (2017 to 2021) arrived years after it had already taken the market. Source: the commit dates above [verified]

- The single decisive change is dated precisely: `borisbstyle` committed "Loop synced to Gyro" on 2015-08-05, creating `src/main/drivers/accgyro/gyro_sync.c`. Before this, the PID loop ran on a fixed timer; after it, the loop runs when the gyro says it has data. Source: `git log --diff-filter=A -- '*gyro_sync*'` on https://github.com/betaflight/betaflight [verified]
- The file's own header block records "Created on: 3 aug. 2015, Author: borisb", so Boris B wrote it two days before committing and two and a half months before Betaflight's first release on 2015-10-29. Source: `git show HEAD:src/main/drivers/accgyro/gyro_sync.c` [verified]
- Gyro-synced looping is therefore the founder's own technical contribution and the most plausible single answer to why Betaflight won on flight feel: it removed the aliasing between an arbitrary loop timer and the gyro's actual output. The file is still in the tree in 2026, carrying his name. Source: the commit and file header above [verified]
- The mechanism is a data-ready flag, not a timer: `gyroSyncCheckUpdate()` returns true only when `gyro->dataReady` has been set by the sensor interrupt, then clears it. The loop rate is thus an emergent property of the gyro part fitted to the board. Source: `git show HEAD:src/main/drivers/accgyro/gyro_sync.c` [verified]
- Because of that design, the choice of gyro chip literally sets the firmware's loop rate, which is the sourced answer to why gyro choice mattered so much. `gyroSetSampleRate()` is a switch statement on the detected sensor. Source: `git show HEAD:src/main/drivers/accgyro/gyro_sync.c` [verified]
- Per-sensor gyro and accelerometer sample rates hard-coded in Betaflight at HEAD: BMI160 3200 Hz gyro and 800 Hz accel; BMI270 3200 Hz or 6400 Hz depending on configuration, 800 Hz accel; ICM-20649 9000 Hz and 1125 Hz; LSM6DSO 6664 Hz and 833 Hz; ICM-45686, ICM-45605 and ICM-56686 6400 Hz and 1600 Hz; and the default path, covering the MPU and ICM-426xx families, 8000 Hz and 1000 Hz. Source: `git show HEAD:src/main/drivers/accgyro/gyro_sync.c` [verified]
- The spread across shipping parts is therefore 3200 Hz to 9000 Hz, nearly a factor of three, on boards that all present as "a Betaflight flight controller" to the buyer. Source: the sample rate table above [verified]
- The ICM-20649 at 9000 Hz is the fastest gyro in the current tree, faster than the ICM-426xx family's 8000 Hz, which contradicts the common assumption that newer always means faster. Source: `git show HEAD:src/main/drivers/accgyro/gyro_sync.c` [verified]
- The LSM6DSO entry carries a developer comment worth quoting for its texture: "6664; // Yes, this is correct per the datasheet. Will effectively round to 150us and 6.67KHz." Source: `git show HEAD:src/main/drivers/accgyro/gyro_sync.c` [verified]
- Note the accelerometer is always run far slower than the gyro, between 800 Hz and 1600 Hz against 3200 Hz to 9000 Hz: attitude estimation does not need the bandwidth that rate control does. Source: the sample rate table above [verified]
- `gyro_sync.c` carries the licence header "This file is part of Cleanflight and Betaflight", preserving the fact that Boris B's gyro-sync work was done inside Cleanflight before the fork. Source: `git show HEAD:src/main/drivers/accgyro/gyro_sync.c` [verified]
- The 2020 formalisation of this design is pull request #9444, "Gyro native rate sampling, filtering, and scheduler restructuring", which shipped in Betaflight 4.2.0 on 2020-06-14: "Restructures the gyro and PID loops to be driven by the native sampling rate for the detected gyro. So for a common Invensense gyro the sampling will always run at 8000hz, for a Bosch BMI160 it will be 3200hz". Source: https://github.com/betaflight/betaflight/pull/9444 [verified]
- Since 4.2 the PID loop is an integer divider off the gyro rate, expressed in code as `gyro.targetLooptime = activePidLoopDenom * 1e6f / gyro.sampleRateHz`. Source: `src/main/sensors/gyro_init.c` on https://github.com/betaflight/betaflight [single]
- The same pull request moved filtering off the gyro rate and onto the slower PID rate purely to save CPU: "Moving the filtering into the PID loop rate saves processing time as it will now run at a lower rate." Source: https://github.com/betaflight/betaflight/pull/9444 [single]
- Betaflight 4.2's default `pid_process_denom` was 8 for F1, 4 for F3, 2 for F411 and 1 for everything else, so an 8 kHz gyro gave an 8 kHz PID loop on an F405 but only 4 kHz on an F411. By 4.4 this simplified to 2 for F411 and 1 for everything else. Source: `src/main/flight/pid.c` at tags 4.2.0 and 4.4.0 on https://github.com/betaflight/betaflight [single]
- Pull request #9444 also set the F411 default overclock to 108 MHz, with the blunt justification "F411 is borderline for processing power and loop stability is greatly improved with this small overclock". Source: https://github.com/betaflight/betaflight/pull/9444 [single]
- Betaflight 4.3 walked F4 guidance back further: "F4 processors should run a 4k PID loop. F411 users should use DShot300, not DShot600, and are blocked from an 8k PID loop. Most F411's should be overclocked to 120Mhz". Source: https://github.com/betaflight/betaflight/releases/tag/4.3.0 [single]

### Motor protocol timing, and why it caps the loop

- Frame times and resulting maximum update rates: standard PWM 1000 to 2000 microsecond pulse at 0.5 kHz; Oneshot125 125 to 250 microseconds at 4 kHz; Oneshot42 42 to 84 microseconds at 11.9 kHz; Multishot 5 to 25 microseconds at 40 kHz; DShot150 106.7 microseconds at 9.4 kHz; DShot300 53.3 at 18.8 kHz; DShot600 26.7 at 37.5 kHz; DShot1200 13.3 at 75.2 kHz. Source: https://oscarliang.com/esc-firmware-protocols/ [single]
- The DShot600 figure checks out arithmetically: a 16-bit frame at 600 kbit per second is 26.67 microseconds. Source: derived from the protocol definition [verified as arithmetic]
- The recommended pairing is protocol to loop rate rather than always-maximum: "2K PID Loop Frequency, use DShot150. 4K PID Loop Frequency, use DShot300. 8K PID Loop Frequency, use DShot600." Source: https://oscarliang.com/esc-firmware-protocols/ [single]
- Bidirectional DShot halves the usable ceiling because the ESC must reply inside the same frame slot: "if bidirectional Dshot is used with Dshot300, the maximum PID loop speed is 4 kHz, and 2 kHz for Dshot150. This does not affect Dshot600." Source: https://github.com/betaflight/betaflight/releases/tag/4.2.0 [single]
- Before 4.2 the legacy default protocol was itself the binding constraint on loop rate: the release notes record that the rework "removed the limitation on the maximum possible PID loop speed imposed by the pre-selected legacy protocol (OneShot125) in earlier versions". Source: https://github.com/betaflight/betaflight/releases/tag/4.2.0 [single]
- All of this timing is dwarfed by the motors themselves, which take "roughly 20ms to 50ms for motors in a 5inch quad to change RPM": the electrical update period is three orders of magnitude shorter than the mechanical response it commands. Source: https://oscarliang.com/esc-firmware-protocols/ [single]
- The RPM filter is what made low loop rates viable: it runs three harmonics per motor per axis, 36 notches in total, and when active Betaflight automatically cuts the dynamic notch count from three to one. Source: https://oscarliang.com/rpm-filter/ [single]
- Betaflight 4.3 still leads its guidance with it: "We recommend using RPM based filtering for best performance". Source: https://github.com/betaflight/betaflight/releases/tag/4.3.0 [single]

### The 2020 to 2023 shortage, measured

- Shortage timeline anchors: onset in early 2020 from COVID disruption plus a 13 percent rise in PC demand, mainstream by 2021-01 when it halted car production, semiconductor lead times peaking at 15 weeks by 2021-02, and flipping to a glut by 2023-07. Source: https://en.wikipedia.org/wiki/2020%E2%80%932023_global_chip_shortage, https://www.bbc.com/news/technology-55704936 and https://www.cnbc.com/2023/07/28/how-the-world-went-from-a-semiconductor-shortage-to-a-major-glut.html [verified]
- TDK published application note AN-000296, "Transitioning from ICM-20602 to ICM-42670-P", archived from 2021-07 under a `/2021/07/` path and still published today: "This document explains how to replace ICM-20602 with ICM-42670-P. The ICM-20602 is NOT pin compatible with ICM-42670-P. PCB redesign is needed." Source: https://web.archive.org/web/20210728112210/https://invensense.tdk.com/download-pdf/an-000296-transitioning-from-icm-20602-to-icm-42670-p/ [single]
- Distributor evidence confirms the MPU-6000's end of life: LCSC holds 418 units at USD 14.84, and every franchise distributor tracked by FindChips shows zero stock while brokers hold it at USD 7.71 to 18.37. Source: https://jlcsearch.tscircuit.com/api/search?q=MPU-6000 and https://www.findchips.com/search/MPU-6000 [verified]
- ICM-20602 shows the same pattern: element14 APAC holds 2,956 units at USD 4.21 to 6.05, Newark and Avnet Abacus are at zero, and broker Win Source holds 110,000 units. Source: https://www.findchips.com/search/ICM-20602 [single]
- TDK's product page for the ICM-20602 now returns 404 while the ICM-42605 and ICM-42688-P pages resolve, consistent with delisting. Source: https://invensense.tdk.com/products/motion-tracking/6-axis/icm-20602/ against https://invensense.tdk.com/products/motion-tracking/6-axis/icm-42605/ [single]
- THE HARDEST EVIDENCE OF SUBSTITUTION, and it is reproducible: 311 of 628 Betaflight board configurations, 49.5 percent, declare two or more distinct gyro part numbers for the same board name. The distribution is 308 configs with one gyro, 175 with two, 90 with three, 42 with four, two with five, one with seven and one with eight. Source: counting `USE_ACCGYRO_*` and `USE_GYRO_SPI_*` defines per `configs/*/*/config.h` in https://github.com/betaflight/config at commit 2b58437 [single, reproducible]
- Betaflight states the semantics explicitly: "A board's IMU defines are a menu, not an assignment. A config declaring MPU6000, ICM42688P and BMI270 is saying any of those three may be fitted; the driver probes each position at boot and binds whichever answers." Source: https://github.com/betaflight/config/pull/1170 [single]
- Gyro part frequency across all Betaflight configs: MPU6000 362, ICM42688P 299, BMI270 171, MPU6500 110, LSM6DSK320X 56, ICM20689 53, LSM6DSV16X 16, ICM42605 14, and ICM20602 just 13. The ICM-20602's near-total absence is the shortage made visible. Source: https://github.com/betaflight/config [single, reproducible]
- Shipping consumer boards carrying four alternative gyros in one config include `HAMO/CRAZYBEEF4FR`, `EMAX/EMAX_TINYHAWKF4SX1280` and `TMTR/TMOTORF7`, each declaring BMI270 plus ICM20689 plus ICM42688P plus MPU6000; `DAFP/DARWINF4SX1280HD` declares seven. Source: https://github.com/betaflight/config/tree/master/configs [single, reproducible]
- The physical enabler for silent substitution is a shared footprint with a different axis convention: "The BMI270 and ICM-42688-P share the LGA-14 PCB footprint but not their sense-axis orientation, so a BMI270 dropped into a board tuned for the 42688 comes up rotated." Source: https://github.com/betaflight/betaflight/pull/15484 [single]
- A named manufacturer request records the motive in full: "Request by AxisFlying due to IMU shortages." Source: https://github.com/betaflight/config/pull/1131 [single]
- Gyro changes under an unchanged board name are documented in the config repository: "The new LUXMINIF7 PCB has the ICM gyro, while the older versions have MPU6k", and "IFLIGHT_F745_AIO v1.1 uses ICM42688P". Source: https://github.com/betaflight/config/pull/685 and https://github.com/betaflight/config/pull/656 [single]
- Betaflight had to write a rule against unmarked swaps, which implies they were happening: "Any board configuration change requiring a user to change configuration behavior must have an accompanying change in marking to indicate (e.g. changing an IMU, or altering the pinout of solder pads)." Source: https://betaflight.com/docs/development/manufacturer/manufacturer-design-guidelines [single]
- Retailers absorbed the ambiguity by putting the gyro in the product name: GetFPV lists the same Diatone Mamba MK4 F722 family as separate BMI270 and ICM42688P SKUs. Source: https://www.getfpv.com/diatone-mamba-stack-mk4-f722-app-fc-55a-3-6s-bheli-32-128k-esc-bmi270.html [single, the page returns 403 to automated fetch and should be checked in a browser]
- The migration sequence in two steps: "By around 2022, more flight controller manufacturers began shifting from the MPU6000 to the BMI270 due to cost and availability issues", then "In 2023, manufacturers again shifted, this time from BMI270 to ICM-42688P". Source: https://oscarliang.com/flight-controller/ [single]
- The shortage moved MCUs too: the STM32G4 was adopted "as an alternative to the F4 MCU due to the global chip shortage in 2021 and 2022", and on ESCs "Manufacturers started using more powerful F3 and F4 MCUs on BLHeli_32 ESCs since 2021, primarily due to the global chip shortage, not for their processing power." Source: https://oscarliang.com/f1-f3-f4-flight-controller/ and https://oscarliang.com/esc/ [single]
- Betaflight now writes second-sourcing into policy, describing the LSM6DSK320X as "a second-source / availability-driven option rather than a performance upgrade" for when the ICM-42688-P "cannot be sourced". Source: https://betaflight.com/docs/development/manufacturer/manufacturer-design-guidelines [single]

### Motor protocols

- Oneshot125 first appears on 2014-11-22 in Ben Hitchcock's commit "Allowing oneshot125 functionality to work on a Naze board", tying the first fast motor protocol to the Naze32 era. Source: `git log --grep='oneshot' -i --reverse` on https://github.com/betaflight/betaflight [verified]
- Oneshot on CC3D needed separate work: Ben Hitchcock's 2014-11-29 commit is "First attempt at getting CC3D PPM to work when oneshot is enabled", which illustrates how per-board timer conflicts drove the protocol work. Source: `git log --grep='oneshot' -i` on https://github.com/betaflight/betaflight [verified]
- Multishot was implemented by `borisbstyle` on 2016-02-23, in commits "Multishot Implementation" and "FastPwm for all oneshot42/125 and multishot // Cleanup", so Multishot is a Betaflight-originated protocol authored by the project founder. Source: `git log --grep='multishot' -i --reverse` on https://github.com/betaflight/betaflight [verified]
- DSHOT was implemented by `blckmn` on 2016-10-13 in the commit "Initial implementation of DSHOT protocol (600 and 150)", and it first shipped in Betaflight 3.1.0 on 2017-01-25. ### Form factors: mounting patterns, stacks and AIOs

- The 30.5 x 30.5 mm M3 pattern originates as the OpenPilot CopterControl house footprint, a 36 x 36 mm board with 30.5 mm hole spacing and 3 mm holes, deliberately shared across CopterControl, CC3D, Revo, GPS, OSD and PipX. Source: https://opwiki.readthedocs.io/en/latest/user_manual/cc3d/cc3d.html [verified]
- CopterControl existed by 2011-04 per the OpenPilot wiki page edit stamp, so the pattern predates the Naze32. Source: https://web.archive.org/web/20120721234423/http://wiki.openpilot.org/display/CC/CopterControl+Home [verified]
- The Naze32 copied it, and that is what made it universal: the rev1 manual, stamped "Create by AbuseMarK 2012" and archived 2012-02-27, specifies "36x36mm" and "M3 mounting hole 30.5mm spacing". Source: https://web.archive.org/web/20120227202825/http://www.abusemark.com/downloads/naze32_rev1.pdf [verified]
- The single most important fact about 30.5 x 30.5: it was NEVER formally standardised. No standards body, consortium or published specification exists; every reachable source treats it as copied convention. Source: absence across all sources consulted [verified negative]
- The 20 x 20 mm pattern appears mid-2016 and originally used M3, not M2: the Furious FPV PIKO BLX manual, cover-dated 2016-06-01, specifies "27x27mm board with 20mm mounting M3 holes". Source: https://images.amainhobbies.com/images/resources/FPV-PIKOBLX/Manuals/1-Piko%20BLX%20FC%20Manual.pdf [verified]
- Corroborated the same summer by the BlueJayF4, sold as "full size, 36x36mm (30.5x30.5 mounting holes) and a 25x25mm (20x20 mounting holes) mini version", whose Betaflight target landed 2016-06-07. Source: https://github.com/betaflight/betaflight.com/blob/master/docs/wiki/boards/archive/BLUEJAYF4.md [verified]
- CORRECTION to a common belief, including one in this document's original brief: 16 x 16 mm is NOT the whoop pattern. 25.5 x 25.5 mm is the whoop and toothpick pattern, and 16 x 16 mm is a separate, smaller nano-stack pattern; vendors sell adapters between the two. Source: https://oscarliang.com/flight-controller/ and https://speedyfpv.com/products/speedyfpv-flight-controller-mount-adapts-30-5mm-25-5mm-20mm-16mm-flight-controllers [verified]
- The "25.5 mm" pattern is really an imperial inch, and the naming is unstable by design: "The real mounting pattern should be 1 inch (25.4mm). But due to the lack of standard, you may see 25.5mm, 26.0mm or even 26.5mm from different manufacturers." Source: https://oscarliang.com/whoop-toothpick-fc/ [verified]
- Betaflight's manufacturer guidelines write it as 25.4, confirming the imperial origin, and list the four "commonly accepted and used board layouts" as "16x16mm for M2 hardware (perpendicularly aligned), 25.4x25.4mm for M2 hardware (typically diagonally aligned), 20x20mm for M2 or M3 hardware (perpendicularly aligned), and 30.5x30.5mm for M3 hardware (perpendicularly aligned)". That document first appeared 2023-12-16, so even the informal codification is recent. Source: https://betaflight.com/docs/development/manufacturer/manufacturer-design-guidelines [verified]
- Betaflight's own current board docs show the drift is still live: SPEEDYBEEF405V4 "30.5 x 30.5 mm (4 mm holes)", IFLIGHT_BLITZ_F7_AIO "25.5 x 25.5 mm", BETAFPVG473 "26 x 26 mm", ORBITF435 and BRAHMA_F405 "M4 30.5x30.5mm". Source: https://github.com/betaflight/betaflight.com/tree/master/docs/wiki/boards/current [verified]
- The 16 x 16 pattern existed by 2018-03-07, per a Thingiverse adapter published that day describing "a 16MMX16MM layout so you can use Racewhoop or other 16x16's". Source: https://www.thingiverse.com/thing:2817812 [verified]
- 16 x 16 became a retail category far later than 20 x 20: RaceDayQuads' 20x20-stacks collection is first captured 2019-03-04, its 16x16-stacks collection not until 2024-04-13. Source: Wayback captures of https://www.racedayquads.com/collections/20x20-stacks and /16x16-stacks [verified]
- Early 4in1 ESCs were wiring-consolidation products, not stack components: the HobbyKing Q Brain 4 x 20A, listed by 2013-12-16, shipped with bullet motor leads and four separate signal wires. Source: https://web.archive.org/web/20131216093627/http://www.hobbyking.com/hobbyking/store/__36674__q_brain_4_x_20a_brushless_quadcopter_esc_2_4s_3a_sbec.html [verified]
- The board-to-board stack as a DESIGNED product appears 2017-03: DYS released an F4 FC plus F30A and F20A 4in1 ESCs where "these two components have interconnection sockets and can be stacked one on another without any wire connection". Source: https://web.archive.org/web/20170513004332/http://www.multirotorguide.com/news/dys-f4-fc-f30a-f20a-4in1-esc-f4-omnibus/ [verified]
- Retail taxonomy dates the transition precisely: GetFPV had no 4in1 or stack category on 2017-06-15, added "4 in 1 ESC's" by 2017-08-01, added "AIO (All in One) FC's" by 2017-11-01, and added "FC / ESC Stacks" between 2018-03-01 and 2018-06-15. Source: Wayback captures of https://www.getfpv.com/ [verified]
- The inversion completed by 2020, when GetFPV renamed its single-ESC category to "Single ESC's", making the individual ESC the qualified special case rather than the norm. Source: https://web.archive.org/web/20200615000000/https://www.getfpv.com/ [verified]
- So the stack answer is: designed stacking from 2017-03, a named retail SKU class by mid-2018, and the default form factor by 2020. Source: synthesis of the three bullets above [verified]
- AIO did not "take over" for whoops, it was the whoop's native form from the beginning: Tiny Whoop was built on the stock Inductrix board, which already integrated FC, brushed drive and receiver. Jesse Perkins: "I created the first Tiny Whoop in 2015 with some friends ... I opened the retail store at TinyWhoop.com in 2016." Source: https://www.tinywhoop.com/pages/about-us [verified]
- Blade Inductrix FPV was announced 2016-08-26 for October 2016 availability, which is when the class went mass market. Source: https://www.rogershobbycenter.com/news/2016/8/26/blade-inductrix-fpv-announced [verified]
- Brushless whoops arrived on AIO boards in 2018, for example the Happymodel Mobula7 on the Crazybee F3 AIO, with the 1S-2S V2.0 on Crazybee F4 V2 PRO dated 2018-10-12. Source: https://www.happymodel.cn/index.php/2018/10/12/happymodel-75mm-2s-brushless-whoop/ [verified]
- AIO pushed up into 5 inch by late 2017: GetFPV's 2017-11-01 homepage features the "Lumenier ALPHA AIO Flight Controller (F4 FC, 4x 30A BLHeli_32 ESC, OSD, PDB, Curr)" at USD 74.99. Source: https://web.archive.org/web/20171101000000/http://www.getfpv.com/ [verified]

### The 8-pin JST-SH connector, and the standard nobody adopted

- CORRECTION to the common belief that no cross-vendor pinout spec exists: one does. The Betaflight Connector Standard mandates JST-SH and fixes the ESC pinout as 1 VBAT, 2 GND, 3 Current, 4 Telemetry, 5 to 8 Motor 1 to 4. Source: https://betaflight.com/docs/development/manufacturer/connector-standard [verified]
- It is recent, and its own change register dates every step: Draft 0.1 2023-04-27, 0.2 2023-05-08, 0.3 2024-06-16, Version 1.0 "Formalize standard" 2025-04-14, 1.1 adding a 10-pin ESC option 2025-04-24, 1.2 reference schematic 2025-05-08, 1.3 2025-12-16, and 2.0 on 2026-08-03. Source: https://betaflight.com/docs/development/manufacturer/connector-standard [verified]
- Version 2.0 of 2026-08-03 removed the 6-pin GPS connector because it was physically identical to the 8 to 26 V digital VTX connector and was destroying GPS modules: a standard written to fix a hazard the standard itself created. Source: https://betaflight.com/docs/development/manufacturer/connector-standard [verified]
- Its stated motivation names the preceding decade's problem exactly: "the lack of standardization has led to compatibility issues between parts. This fragmentation has made it challenging for users to build and maintain multi-rotor drones." Source: https://betaflight.com/docs/development/manufacturer/connector-standard [verified]
- Adoption is currently near zero. Betaflight's own current board documentation carries a `connector_standard` field, and the boards that have it all read `false`, including SPEEDYBEEF405V4, FOXEERH743 and GEPRCF722. Source: https://github.com/betaflight/betaflight.com/tree/master/docs/wiki/boards/current [verified]
- Vendors accordingly still warn buyers directly: "Manufacturers often use different/incompatible pinout standards", and separately "when using ESC and FC from different brands ... the pinouts might be different, requiring rearrangement of the wires". Source: https://aerocogito.github.io/h7-digital-docs/docs/hardware/pinout/ and https://oscarliang.com/flight-controller/ [verified]
- The same 8-pin JST-SH crossed into the autonomy branch: ARK's 4in1 ESC for ArduPilot lists an "8 Pin JST-SH Input/Output Connector". Source: https://ardupilot.org/plane/docs/common-ark-4in1-esc.html [verified]

## Unknowns / could not verify

- timecop, dongie and GitHub user `trollcop` are the same person, based in Japan, sharing one email address. His full legal name is not established and is not asserted.

- The exact Betaflight fork date cannot be derived from git merge-base, because Cleanflight back-merged Betaflight in 2020, which moves the merge-base to 2020-06-14. Repository creation date (2015-06-08) and earliest Boris B commit (2015-05-01) are the usable bounds.
